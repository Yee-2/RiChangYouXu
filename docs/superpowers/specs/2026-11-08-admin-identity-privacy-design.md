# 后台独立入口、账号标识与邮箱隐私设计

日期：2026-11-08

状态：用户已确认；2026-11-08 补充确认管理员独立表、6 位数字 UID 和后台账号管理功能

项目：日常有序（RiChangYouXu）

## 1. 背景与现状

- 普通 App 与后台目前由同一前端入口提供，后台通过 `/#/admin` hash 路由进入；没有独立的后台登录页。
- 后台需要已有 Supabase 会话，再读取 `profiles.role` 判断是否为管理员。
- `profiles.id` 当前是 Supabase Auth 用户 UUID，已经作为内部主键和外键使用；资料表没有邮箱列，但资料查询策略允许公开读取资料字段。
- 注册触发器会从邮箱前缀生成默认昵称；社区账户资料区域也会直接展示登录邮箱。
- 管理员角色不能由普通客户端直接修改。现有管理员审核通过 Edge Function 执行，并写入 `moderation_audit`。

## 2. 目标

1. 后台在 `https://admin.yeecc.cn` 独立访问，不显示 App 的底部导航和普通社区入口。
2. 未登录时显示邮箱和密码登录页；没有管理员注册入口；提供忘记密码和重设密码流程。
3. 后台可将已注册账号加入管理员，也可撤销管理员授权；权限变化需要二次确认、填写原因并写入审计记录。
4. 每个账号有系统生成、稳定且可公开展示的 6 位纯数字 UID，数据库确保唯一。数据库内部继续用 Supabase UUID 关联数据。
5. 新用户获得系统随机昵称，可在个人资料中自行修改；昵称不从邮箱推导。
6. 普通用户的个人页只显示掩码后的本人邮箱，公开主页和社区数据不提供邮箱；只有经过服务端管理员鉴权的后台接口可以返回完整邮箱。

## 3. 方案比较与选定

### A. 独立子域名，共用现有 Worker 和 Supabase（选定）

将 `admin.yeecc.cn` 绑定到现有 `richangyouxu` Cloudflare Worker，并在前端按 hostname 展示独立后台入口。两个子域名共用代码发布和 Supabase 项目，后台仍有独立登录、独立页面入口和服务器端角色校验。维护成本较低，符合当前单一应用部署方式。

Cloudflare Workers 文档支持为同一 Worker 配置多个 Custom Domain；绑定后 Cloudflare 会创建对应 DNS 记录。Supabase Auth 的密码重置跳转必须配置在 Redirect URLs 允许列表中。[Cloudflare Workers Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/) · [Supabase Auth Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls)

### B. 后台独立 Worker

后台单独构建和部署，仍连接同一个 Supabase 项目。部署与发布边界更独立，但需要维护第二个 Worker、发布配置和环境变量。

**本次采用 A。** 如果现有 Worker 的部署配置不能安全地服务两个 hostname，再在实现阶段评估 B；不改变已确认的用户访问域名。

## 4. 页面和认证流程

### 4.1 域名分流

- `daily.yeecc.cn` 继续显示普通 App。
- `admin.yeecc.cn` 只显示后台登录、密码恢复和管理员工作台，不渲染普通 App 导航。
- 普通 App 中旧的 `/#/admin` 入口改为跳转 `https://admin.yeecc.cn/`，不在普通站点内保留可直接打开的管理工作台。

### 4.2 后台登录

- 登录页字段：邮箱、密码；操作：登录、忘记密码。
- 不显示注册或邀请注册入口。
- 使用现有 Supabase Auth 用户体系，不另建管理员密码表。
- 登录成功后由受保护的服务端接口检查用户是否在独立 `admin_accounts` 表中，且账号状态为 `active`。`profiles.role` 仅作兼容字段，不单独授予后台权限。非管理员或受限制账号立即清除后台会话并显示无权限提示；不得进入工作台。
- 后台所有数据与变更接口继续在服务端检查管理员身份，不能依赖前端路由或按钮显隐。

### 4.3 忘记密码

- 登录页提交邮箱后调用 Supabase Auth 密码重置，目标跳转为后台域名上的恢复页。
- 恢复页校验 Supabase 的密码恢复会话后允许设置并确认新密码；没有有效恢复会话时提示重新申请邮件。
- Supabase URL Configuration 增加精确的后台恢复地址，例如 `https://admin.yeecc.cn/`（或实现中采用的固定恢复路径），不要使用不必要的宽泛通配符。
- 邮箱提示采用不泄漏账号是否存在的通用文案。

## 5. 用户 UID 与默认昵称

### 5.1 短 UID

- 在 `profiles` 新增 `uid` 字段，格式为 6 位纯数字。
- 数据库生成 UID，建立唯一约束；新用户由注册触发器生成，现有用户由增量迁移回填。冲突时重新生成，确保唯一。
- UID 创建后不可由客户端修改；个人页、公开用户主页和后台账号管理均可查看。后台可通过 UID 精确查找用户。
- 现有 `profiles.id` UUID 保留作为 Auth 关联键和数据库外键，不作为用户可编辑资料。

### 5.2 随机昵称

- 新用户注册时不再把邮箱前缀写入 Auth metadata。数据库触发器为账号生成中性随机昵称，例如“有序伙伴 7K2M”；昵称可以重复，UID 保证身份唯一。
- 用户仍可在“我的 → 账号设置”中修改昵称。
- 迁移时只替换明显由旧逻辑产生的邮箱前缀昵称或默认占位昵称，保留其他已有自定义昵称。

## 6. 邮箱隐私与后台管理员管理

### 6.1 普通 App 与社区

- `profiles` 不新增邮箱字段；社区资料查询和 `Profile` 类型只包含 UID、昵称、头像、简介等公开资料。
- 社区主页、动态、评论、关注列表和话题页不展示邮箱。
- “我的”账号设置只显示掩码后的本人邮箱，例如 `ab***@example.com`；不在普通 App 的个人资料卡片展示完整地址。
- Supabase Auth 的邮箱仍用于邮箱密码登录和重置。邮箱可在当前用户自己的 Auth 会话对象中存在；本设计保证普通界面不展示完整值、普通社区查询拿不到其他人的邮箱。若要求连账号本人浏览器也无法读取自己的 Auth 邮箱，则需要更换认证代理架构，超出本期范围。

### 6.2 管理员身份与账号管理

- `admin_accounts` 与普通 `profiles` 分离保存管理员身份；启用 RLS，普通用户不能读写，管理员身份只由服务端维护。Auth 仍使用统一 Supabase 登录体系，但管理员不能从后台注册页注册。
- 管理后台有独立的“用户管理”和“管理员账号”页签。用户管理可按 6 位 UID/邮箱搜索、按账号状态筛选及按注册时间排序；管理员账号显示完整邮箱。
- 已有 active 管理员可以将**已注册且已验证邮箱**的普通账号加入管理员表，也可撤销管理员；添加/撤销填写原因并二次确认，操作记录包含操作者、目标、动作、原因和时间。
- 管理员列表可对其他管理员设置新密码；要求二次确认并填写原因，服务端通过 Auth Admin API 更新并写审计，不读取旧密码。管理员可从右上角菜单修改自己的密码或退出登录。
- `admin-manage` Edge Function 验证调用者 JWT 并确认操作者存在于 `admin_accounts` 且 profile 状态 active；只有函数使用服务角色读取 `auth.users` 邮箱、管理账户并调用 Auth Admin API。服务角色密钥不得进入浏览器。
- 数据库侧的管理员变更 RPC 在一个事务内验证目标和最后一位 active 管理员规则、更新管理员表并写审计记录，避免权限更新成功但审计写入失败。RPC 只允许服务角色调用；Edge Function 只返回分页或精确查找所需字段，不提供未筛选的全量邮箱导出。
- 普通用户、暂停账号和封禁账号均不能调用管理员接口。管理员新增或撤销保留审计日志。
- 第一位管理员继续由项目所有者通过可信的 Supabase 管理流程初始化；之后使用后台管理。

## 7. 数据库与后端变更

新增一份向前兼容的 Supabase 增量迁移，预计包括：

1. `profiles.uid` 字段、唯一索引、生成逻辑及存量回填。
2. 注册触发器的随机昵称逻辑与旧邮箱前缀昵称修复。
3. 确保 Auth email 不进入公开资料表或普通 REST 查询；保留既有角色字段保护和 RLS。
4. 建立仅服务角色可访问的 `admin_accounts` 表；调整管理员校验与 RLS，并提供服务角色受限的筛选/排序账号查询及原子化管理员变更审计函数。
5. 为管理员角色变化记录审计动作；必要时扩展可接受的操作类型约束（如有）。
6. 不向客户端授予 `profiles.role` 的直接更新权限。

新增受保护的管理员管理 Edge Function；前端提供管理员登录、恢复密码、管理员角色管理界面，并更新 API 文档、产品说明书和部署说明。

## 8. 验收标准

- 打开 `admin.yeecc.cn` 未登录时显示仅含登录和忘记密码入口的后台页面，没有注册功能和 App 底部导航。
- 普通账号无法进入后台；登录后会话被清除并得到明确提示。active 管理员能够进入现有审核工作台。
- 后台密码重置邮件能返回后台恢复页；普通 App 的邮箱验证/登录跳转继续工作。
- 注册用户获得唯一 6 位纯数字 UID 和不含邮箱信息的随机昵称；旧用户 UID 回填成功，自定义昵称保留，旧邮箱前缀昵称被替换。
- 用户可自行修改昵称，不能修改 UID。
- 普通资料 API/社区页面无完整邮箱；本人账号设置只显示掩码邮箱；管理员查询接口只对 active admin 返回完整邮箱。
- 管理员可通过 UID 或邮箱为已注册用户添加管理员，也可撤销授权；每次权限变化均有审计记录。普通用户直接调用 Edge Function 被拒绝，最后一个 active admin 不能被撤销。
- `admin_accounts` 为管理员权限唯一来源；用户管理和管理员账号分开显示。用户列表支持账号状态筛选和注册时间排序；后台顶栏显示管理员名称/邮箱并提供修改本人密码、退出登录菜单；管理员列表支持为其他管理员重置密码并记录原因。
- 普通站点的 `/#/admin` 不再直接打开后台工作台。
- `npm run build` 成功；部署文档列明 Cloudflare 与 Supabase 所需配置。

## 9. 部署配置

1. 在现有 Cloudflare Worker `richangyouxu` 添加 Custom Domain `admin.yeecc.cn`，并确认 DNS 与 HTTPS 正常。
2. 在 Supabase Authentication → URL Configuration 增加后台密码恢复所用的精确 Redirect URL。
3. 应用新增数据库迁移并部署 `admin-manage` Edge Function。
4. 确认首位 active admin 可登录后台；再从后台添加其余管理员。

具体 Cloudflare 与 Supabase 控制台步骤会写入产品部署文档。域名和生产数据库变更在实现完成后单独核对，不在本设计文档提交时执行。

## 10. 不在本期范围

- 非注册用户的管理员邀请注册。
- 更换邮箱、手机号登录、社交登录或独立认证服务。
- 对社区用户隐藏公开 UID。
- 将公开 UID 替换成数据库外键；帖子、评论、关注等关系仍使用现有 Supabase UUID。
- 多级管理员、审批链、自动审核或申诉工作流。

## 11. 自审

- **权限边界**：角色授予/撤销与读取完整邮箱只在服务端函数完成；客户端直接改角色继续被禁止。
- **隐私边界**：公开 profile 没有 email 字段；普通 UI 掩码本人邮箱，社区视图不渲染邮箱；完整邮箱仅由管理员接口按需返回。
- **迁移兼容**：保留现有 UUID 外键和自定义昵称；UID 为新增字段并迁移回填。
- **恢复流程**：后台恢复链接有固定 Redirect URL，并在 Supabase allowlist 中显式配置。
- **生产限制**：实现并构建通过不代表 Cloudflare 域名、Supabase 迁移或 Edge Function 已在线配置；上线前按部署步骤执行并验证。
