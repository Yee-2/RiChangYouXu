## 1. 文档说明

### 1.1 目的

本文档定义“日常有序”当前发布版本的完整产品需求、业务规则、数据边界、接口要求、安全要求、非功能要求和验收标准。它可以用于：

- 产品范围确认与变更评审。
- 前后端联合开发与联调。
- 测试用例设计、发布验收和回归检查。
- 运维、安全、隐私和内容治理检查。
- 后续版本的需求追踪与影响分析。

### 1.2 需求用语

- **必须**：当前发布版本不可省略的要求。
- **应当**：默认执行；若不能满足，必须记录原因和替代方案。
- **可以**：增强项，不影响本期核心交付。
- **不在本期范围**：明确排除，不能据此验收当前版本。

### 1.3 需求依据

需求优先级如下：

1. 当前源代码、Supabase 迁移、Edge Function 和生产配置。
2. 已确认的[产品与技术设计](superpowers/specs/2026-11-08-life-companion-design.md)。
3. 已确认的[后台、UID 与邮箱隐私设计](superpowers/specs/2026-11-08-admin-identity-privacy-design.md)。
4. [接口文档](api.md)、[产品使用与部署指南](product-guide.md)和当前 README。
5. 隐私政策、用户协议和社区规范草稿。

若历史设计文档与当前实现冲突，以已上线并经过验收的实现为当前基线；冲突会在“当前限制与风险”中明确，而不是静默扩写成已实现功能。

### 1.4 当前发布定义

当前版本是一个手机优先的生活管理 H5/PWA，包含：

- 四个默认离线可用的个人模块：生活清单、出门检查、水电燃气抄表、宠物日常。
- 本机 JSON 备份、预览、合并恢复和清除。
- 可选的 Supabase 邮箱账号与在线社区。
- 独立管理后台、内容审核、账号治理、管理员管理和审计记录。
- Cloudflare 双域名静态发布与 Supabase 托管后端。

## 2. 产品概述

### 2.1 产品定位

“日常有序”面向希望把计划、家庭记录、宠物照护和轻量社区放在同一入口中的个人用户。产品优先保证个人记录的低摩擦和离线可用，社区与管理能力作为可选的在线扩展。

### 2.2 产品目标

- 让用户能在手机浏览器或主屏幕应用中快速记录和管理日常事务。
- 把今天需要关注的事项放在首页，降低查找成本。
- 让个人数据默认留在设备上，并通过可验证的备份降低数据丢失风险。
- 提供以生活分享为主题的小规模社区，而不是泛化社交平台。
- 以服务端权限、RLS 和审计记录支撑可追踪的内容治理。
- 保持单人或小团队可维护的部署结构，避免不必要的基础设施。

### 2.3 成功标准

- 未配置社区后端时，四个个人模块仍可完整运行。
- 刷新、关闭页面或离线后，已保存的本机记录仍然存在。
- 用户可在移动端完成主要任务，无需缩放或横向滚动。
- 社区用户能够完成认证、发布、互动、举报和账号管理。
- 普通用户无法通过前端状态修改管理员数据或执行管理员动作。
- 所有审核、账号限制和管理员权限变更都有可查询的审计记录。
- 生产构建、数据库 lint、迁移历史和关键浏览器流程可验证。

### 2.4 不在本期范围

- 家庭共享、多人协作清单或组织空间。
- 个人数据云同步、跨设备自动同步和冲突合并。
- Android/iOS 原生应用。
- 手机号、社交账号或企业单点登录。
- 私信、群聊、实时音视频。
- 自动内容识别、申诉工作流或多级审核。
- 付费订阅、广告、商城或佣金系统。
- 宠物医疗诊断、费用自动估算或第三方设备接入。

## 3. 用户与角色

| 角色 | 定义 | 核心能力 |
|---|---|---|
| 本机用户 | 无需登录即可使用个人模块 | 管理本机清单、检查、抄表、宠物和备份 |
| 社区访客 | 未登录用户 | 在普通 App 中看到社区登录引导，不展示社区内容流 |
| 社区用户 | 使用已验证邮箱登录 | 浏览社区、发布互动、管理本人资料、举报和注销账号 |
| 暂停用户 | `suspended` 且暂停期未结束 | 可读取本人可见数据，不能执行社区写操作 |
| 永久封禁用户 | `banned` | 可读取允许内容，不能发布互动，只能由管理员解封 |
| 管理员 | `admin_accounts` 中存在且 profile 为 active | 内容审核、账号治理、管理员管理、查看审计和完整邮箱 |
| 项目所有者 | 可访问 Supabase 与 Cloudflare 管理控制台 | 初始化首位管理员、管理托管凭据和应用部署 |

### 3.1 权限原则

- 本机用户权限不依赖社区登录。
- 登录身份与业务授权分离。登录成功不代表拥有管理员权限。
- 管理员权限唯一来源是 `public.admin_accounts`，`profiles.role` 只保留兼容和展示意义。
- 客户端按钮隐藏只能改善体验，不能代替服务端鉴权。
- service-role/secret key 只能存在于服务端，不得进入浏览器、本机环境文件或 Git。

## 4. 产品结构与运行边界

### 4.1 普通 App 信息架构

底部导航固定包含五个入口：

| 导航 | 内容 |
|---|---|
| 首页 | 当地问候、今日待办、今日完成、最近抄表、宠物提醒、出门检查快捷入口 |
| 清单 | 生活清单、事项、出门检查模板和进行中的检查 |
| 记录 | 水电燃气表具与读数、宠物档案与事件 |
| 社区 | 社区访问、动态流、话题、关注、举报和账号页 |
| 我的 | 账号资料、主题、本机备份、本人动态、关注和举报 |

### 4.2 生产入口

- 普通 App：`https://daily.yeecc.cn/`
- 独立管理后台：`https://admin.yeecc.cn/`

两个域名由同一个 Cloudflare Worker 和同一份前端产物提供，应用按 hostname 分流。后台不得在普通 App 底部导航中出现。普通 App 访问旧 `/#/admin` 时必须跳转到独立后台域名。

### 4.3 离线边界

- 个人模块在 PWA 静态资源缓存成功后可离线读写。
- 社区、账号和管理员操作要求在线，不能伪造离线成功。
- PWA 缓存不替代个人数据备份。
- 浏览器存储被用户清理或设备损坏时，本机数据可能永久丢失。

### 4.4 时区与日期

- 日期输入使用设备本地日历日，格式为 `YYYY-MM-DD`。
- 首页“今天”的判断必须使用设备本地日期，不得直接截取 UTC 日期。
- 数据库时间字段使用 `timestamptz`，接口传输 ISO 8601 时间。
- 暂停到期、审计时间和内容时间由服务端时间判断。

## 5. 功能需求

### 5.1 应用外壳、主题与响应式界面

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-SHELL-001 | 普通 App 必须提供首页、清单、记录、社区、我的五个主导航 | 五个入口可切换；当前入口有可见选中态和 `aria-current` |
| FR-SHELL-002 | 应用必须支持日间、夜间和跟随系统三种主题来源 | 首次访问跟随系统；切换后持久化；刷新后保留 |
| FR-SHELL-003 | 界面必须适配手机和桌面视口 | 最小支持 320px 宽度；390×844 和桌面视口无横向溢出 |
| FR-SHELL-004 | 关键图标按钮必须具有可访问名称 | 屏幕阅读器可识别；不能只依赖颜色表达状态 |
| FR-SHELL-005 | 应用必须使用函数式 PWA 清单、图标和自动更新 Service Worker | 可安装；静态资源可预缓存；离线打开不显示空白页 |
| FR-SHELL-006 | 操作结果必须通过加载、空数据、错误、成功或离线状态反馈 | 不出现无反馈提交或虚假成功 |
| FR-SHELL-007 | 首页问候必须按设备本地时间显示早上、中午、下午、晚上或夜深 | 时钟跨时间段后无需刷新即可更新 |

### 5.2 生活清单

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-LIST-001 | 用户必须可创建、重命名、归档、恢复和删除清单 | 标题非空且不超过 60 字；归档清单仍可恢复 |
| FR-LIST-002 | 删除清单必须同时删除其事项，并在操作前确认 | 不会遗留孤立事项 |
| FR-LIST-003 | 用户必须可在清单中添加事项，填写标题、可选截止日期和可选备注 | 标题 1–100 字；备注最多 500 字 |
| FR-LIST-004 | 勾选事项时记录完成时间，取消完成时清除本次完成时间 | `done` 与 `completedAt` 始终一致 |
| FR-LIST-005 | 首页必须显示未完成且截止日期为空或已到期的活动清单事项 | 最多直接展示 4 项；已归档清单不参与 |
| FR-LIST-006 | 首页必须统计当天完成的活动清单事项并显示总进度 | 前一天完成的事项不进入当天分母 |
| FR-LIST-007 | 用户必须可从旅行和搬家示例创建预填清单 | 示例事项随清单一起生成 |
| FR-LIST-008 | 清单页必须按未完成优先展示事项 | 完成事项仍有可见状态，不丢失历史 |

### 5.3 出门检查

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-CHECK-001 | 用户必须可创建、编辑、复制和删除检查模板 | 模板标题非空且不超过 60 字；至少有一个检查项 |
| FR-CHECK-002 | 首次使用且无模板时，应用必须创建上班、健身、短途出行三个默认模板 | 仅在模板总数为零时创建，避免重复初始化 |
| FR-CHECK-003 | 开始检查时必须从模板复制为独立检查实例 | 修改模板不改变已开始实例 |
| FR-CHECK-004 | 检查进度必须持久化到本机 | 离开页面、刷新或离线后仍保留 |
| FR-CHECK-005 | 所有项目完成时必须记录 `completedAt`；取消任一项目时必须清除完成时间 | 完成和进行中状态可逆 |
| FR-CHECK-006 | 删除模板不得删除历史或进行中的检查实例 | 删除只影响模板本身 |
| FR-CHECK-007 | 首页和清单页必须能看到进行中实例及完成比例 | 进行中实例可直接勾选 |

### 5.4 水电燃气抄表

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-METER-001 | 用户必须可新增水表、电表或燃气表 | 名称非空且不超过 50 字；单位必填 |
| FR-METER-002 | 用户必须可按表具记录非负读数、日期和可选备注 | 日期必填；备注最多 200 字 |
| FR-METER-003 | 新读数日期必须晚于同一表具上一条记录 | 相等或更早日期被拒绝并给出明确提示 |
| FR-METER-004 | 新读数不得小于同一表具上一条读数 | 不允许生成负用量 |
| FR-METER-005 | 同一表具相邻两个有效读数必须计算期间用量 | 展示最近读数、日期和上期用量 |
| FR-METER-006 | 首页必须显示最近一条全局抄表记录及其表具信息 | 无记录时显示引导状态 |
| FR-METER-007 | 本功能不自动估算费用，不接入第三方表具 | 不得展示未经数据支持的账单结论 |

### 5.5 宠物日常

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-PET-001 | 用户必须可新增宠物档案 | 名字必填且不超过 40 字；种类默认“猫咪”且不超过 40 字 |
| FR-PET-002 | 宠物档案必须支持可选生日和备注 | 生日使用本地日期；备注只作信息记录 |
| FR-PET-003 | 用户必须可为宠物记录喂养、体重、疫苗、驱虫、就诊或自定义事件 | 事件标题必填，最多 100 字 |
| FR-PET-004 | 宠物事件必须记录事件日期，并可设置可选提醒日期 | 提醒为一次性日期，不实现周期重复 |
| FR-PET-005 | 未完成且带提醒日期的事件必须按日期排序显示在记录页 | 逾期项标记已逾期并持续保留 |
| FR-PET-006 | 首页必须显示最近的未完成宠物提醒 | 无提醒时显示引导信息 |
| FR-PET-007 | 用户必须可标记提醒完成和恢复未完成状态 | 完成状态本机持久化 |
| FR-PET-008 | 产品不得生成宠物医疗诊断或治疗建议 | 界面只呈现用户录入信息 |

### 5.6 本机备份与恢复

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-BACKUP-001 | 用户必须可导出 `schemaVersion: 1` JSON 备份 | 文件名包含本地日期；包含全部个人数据 store，不含偏好设置 |
| FR-BACKUP-002 | 导入前必须完成解析和全量校验，再显示预览 | 预览包含导出时间、总记录数、各 store 新增和覆盖数量 |
| FR-BACKUP-003 | 导入文件不得超过 20 MB | 超限立即拒绝 |
| FR-BACKUP-004 | 校验必须覆盖版本、导出时间、字段类型、长度、日期、唯一 ID 和关联外键 | 清单事项、表具读数、宠物事件不得引用不存在的父记录 |
| FR-BACKUP-005 | 导入必须使用单个 IndexedDB read/write transaction | 任一写入失败时现有数据不被部分修改 |
| FR-BACKUP-006 | 导入策略必须为合并：同 ID 覆盖，其他本机记录保留 | 预览数量与实际导入结果一致 |
| FR-BACKUP-007 | 清除本机记录必须二次确认并提醒先备份 | 清除个人 store，不删除 Supabase 社区账号 |
| FR-BACKUP-008 | 备份不得包含邮箱、密码、Supabase 会话或线上社区内容 | 私密信息不进入普通 JSON 备份 |

### 5.7 邮箱账号与登录

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-AUTH-001 | 用户必须可使用邮箱和密码注册，并通过邮箱验证码完成验证 | 未验证邮箱不能正常登录 |
| FR-AUTH-002 | 用户必须可使用邮箱验证码登录；新邮箱验证后可创建无密码账号 | `shouldCreateUser: true`；验证码类型为 `email` |
| FR-AUTH-003 | 密码必须至少 8 位且同时包含至少一个英文字母和一个数字 | 前端和后端使用一致规则 |
| FR-AUTH-004 | 恢复、设置或修改密码必须验证 6 位邮箱验证码 | 完成后退出当前会话并要求重新登录 |
| FR-AUTH-005 | 验证码有效期必须为 10 分钟，发送间隔至少 60 秒 | 页面显示倒计时；错误和重发可理解 |
| FR-AUTH-006 | 账号必须提供验证码登录、密码登录、忘记密码、注销和退出 | 页面入口完整，不能出现空操作 |
| FR-AUTH-007 | 本人邮箱只能以掩码形式显示 | 完整邮箱不出现在普通社区或公开资料中 |
| FR-AUTH-008 | `user_auth_settings.password_set` 必须用于区分“设置密码”和“修改密码” | 无密码账号设置后状态更新 |
| FR-AUTH-009 | 若启用泄露密码保护，应由 Supabase Auth 拒绝已知泄露密码 | 该能力仅适用于支持的 Supabase 套餐 |

### 5.8 社区资料与主页

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-PROFILE-001 | 系统必须为每个账号生成唯一 6 位数字 UID | UID 唯一、不可由客户端修改 |
| FR-PROFILE-002 | 新账号必须获得随机、中性且不含邮箱或 UID 的默认昵称 | 数据库触发器生成；用户可修改 |
| FR-PROFILE-003 | 用户必须可修改昵称、简介和头像 | 昵称 1–40 字；简介最多 240 字 |
| FR-PROFILE-004 | 头像必须支持 JPG、PNG、WebP，最大 2 MiB | 上传失败时保留原头像并清理新文件 |
| FR-PROFILE-005 | 公开主页必须显示昵称、用户名、头像、简介、动态和关注统计 | 不展示 UID 或邮箱 |
| FR-PROFILE-006 | 用户必须可查看本人关注列表并取消关注 | 列表支持分页；空状态清晰 |
| FR-PROFILE-007 | 普通 App 只向后台和管理员查询接口提供 UID | 用户端查询不请求 UID |

### 5.9 社区动态、话题与互动

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-COMM-001 | 未登录普通 App 必须显示社区登录引导，不展示动态流 | 登录后才请求和显示社区内容 |
| FR-COMM-002 | 已验证且 active 的用户必须可发布文字、图片和 `#话题` 动态 | 正文最多 5,000 字；最多 9 张图片 |
| FR-COMM-003 | 动态必须至少包含正文或图片之一 | 空内容被数据库和业务层拒绝 |

## 6. 业务规则与状态模型

### 6.1 账号状态

| 状态 | 含义 | 登录 | 社区读取 | 社区写入 | 后台访问 |
|---|---|---:|---:|---:|---:|
| `active` | 正常账号 | 是 | 是 | 是 | 仅管理员 |
| `suspended` | 暂停中，未到期 | Supabase Auth ban 期间不可新登录 | 已有会话可读 | 否 | 否 |
| `suspended` 且已到期 | 暂停到期，有效状态恢复 | 是 | 是 | 是 | 数据库原值仍可为 suspended，界面按过期计算 active |
| `banned` | 永久封禁 | 受限 | 按已有会话/RLS | 否 | 否 |
| `deleted` | 账号已删除 | 否 | 公开资料不可见 | 否 | 否 |

规则：

- 管理员必须同时满足 `admin_accounts` 成员和 profile `active`。
- 暂停操作同时写入 profile 截止时间和 Supabase Auth `ban_duration`。
- 数据库 `is_active_user()` 必须识别暂停已过期，避免只依赖 Auth ban。
- 永久封禁在 Auth 中设置长期 ban，业务状态保持 `banned`。
- 删除账号通过 Auth Admin API 删除用户，依赖外键级联清理关联数据。

### 6.2 内容状态

```text
visible -> hidden -> visible
visible -> hidden -> removed
visible -> removed
hidden  -> removed
removed -> 终态
```

- `visible`：符合可见条件，可读取和互动。
- `hidden`：对普通用户不可见；作者和管理员可识别处理状态。
- `removed`：内容已移除，不允许恢复或再次审核。
- 删除动态时，其评论先隐藏；媒体清理完成后再将动态和评论标记 removed 或删除数据库记录。

### 6.3 举报状态

```text
open -> handled
open -> dismissed
```

- `open`：待处理。
- `handled`：管理员已处理，`review_reason` 为空。
- `dismissed`：管理员驳回，必须保存可展示给举报人的原因。
- 针对内容或账号处理时如果传入 `reportId`，成功动作同时更新举报状态。

### 6.4 清单与检查状态

- 未完成事项：`done = false`，`completedAt` 不存在。
- 完成事项：`done = true`，`completedAt` 为完成时刻。
- 取消完成：恢复 `done = false` 并清除 `completedAt`。
- 检查实例：任意项目未完成时 `completedAt` 不存在；全部项目完成时写入 `completedAt`。
- 已归档清单不再进入首页待办和进度，但数据仍保留。

### 6.5 管理员边界

- 首位管理员只能由项目所有者通过可信 SQL/Auth 流程初始化。
- 后续管理员只能从已验证邮箱且 active 的现有普通用户中添加。
- 管理员和普通用户的身份字段均不能由客户端直接修改。
- 管理员不能自助删除账号，也不能通过治理接口暂停或封禁其他管理员。
- 最后一位 active 管理员不可撤销。

### 7.3 数据保留和删除

- 个人数据保留到用户清除本机数据或手动删除对应记录。
- 隐藏内容保留供作者和管理员核查；移除内容不再可恢复。
- 删除动态会删除或级联清理评论和话题关系。
- 删除账号删除线上身份和社区内容，本机数据保留。
- 审计日志必须保留，不因普通内容删除而自动消失。
- 运营者上线前必须补充 Supabase、Resend、日志和备份的实际保留策略。

### 7.4 数据一致性

- 本机记录使用 UUID；同 ID 的备份导入是覆盖语义。
- 云端关系使用 Auth UUID；6 位 UID 只用于身份展示和后台查找。
- 动态、评论、举报和审计的目标 ID 保持 UUID。
- 删除父记录必须依赖外键或服务端逻辑清理子记录和媒体。
- 内容状态不能通过普通作者直接设置；由服务端管理动作控制。

## 8. 接口与后端需求

### 8.1 后端组成

- **Supabase Auth**：邮箱注册、OTP、密码登录、恢复、会话和 Auth ban。
- **PostgREST**：受 RLS 和列级权限保护的数据 API。
- **Storage**：私有 `community-media` bucket 和签名 URL。
- **Edge Functions**：
  - `admin-moderate`：内容和账号审核。
  - `admin-manage`：管理员身份、账号查询和密码管理。
  - `delete-content`：用户清理自己的内容与媒体。
  - `delete-account`：删除线上账号和社区数据。
- **Cloudflare Worker Static Assets**：普通 App 和后台共用 SPA 产物、双自定义域名和 SPA fallback。

### 8.2 鉴权要求

- 所有 Edge Function 必须启用 `verify_jwt = true`。
- 客户端必须通过 `Authorization: Bearer <user_access_token>` 传递用户会话。
- publishable/anon key 必须进入 `apikey` 头，不得作为 Bearer token。
- 函数内部必须使用 `auth.getUser()` 验证用户，不得仅信任 JWT 字符串或前端参数。
- 管理函数必须再查询 `admin_accounts` 和 profile 状态。
- 用户删除函数必须校验内容归属和账号 active 状态。
- 普通客户端不得直接更新 `profiles.role`、`uid`、`account_status` 或管理员表。

### 8.3 API 约定

- 路径、字段和错误码以[接口文档](api.md)为准。
- PostgREST 基础路径为 `{SUPABASE_URL}/rest/v1`。
- Edge Function 路径为 `{SUPABASE_URL}/functions/v1/{name}`。
- JSON 字段使用 camelCase 作为函数请求字段，数据库列使用 snake_case。
- 所有写操作必须验证必填字段、长度和允许值。
- 图片上传成功后仍需在数据库写入失败时执行清理。
- 重复点赞、重复关注和并发话题创建必须可安全重试。

### 8.4 RLS 要求

- `public` 中所有业务表必须启用 RLS。
- profiles 可公开读取未注销资料，但客户端只能更新本人允许列。
- posts/comments 只允许读取 visible、本人 visible/hidden 或管理员范围。
- likes 和 follows 可公开读取，但写入必须绑定 `auth.uid()` 和 active 状态。
- reports 只允许举报人读取本人记录；管理员可读全部。
- moderation_audit 只允许管理员读取；写入必须经服务端函数。
- admin_accounts 不得向 anon/authenticated 授予读写权限。
- user_auth_settings 只允许 authenticated 读本人行，不允许客户端写入。
- Storage 写入路径必须属于当前用户；读取头像或可见内容需要对应策略。
- RLS 策略和 Storage 策略必须在迁移中版本化。

### 8.5 Edge Function 特定约束

#### `admin-manage`

- 仅 active 管理员调用。
- 管理员跨域来源限定为后台域名和本地开发地址。
- 精确查找只接受 6 位 UID 或邮箱。
- 分页上限 100。
- 非管理员、暂停或封禁账号返回 403。
- 密码重置不记录或返回旧密码。

#### `admin-moderate`

- 必须校验操作者、目标类型、目标 ID 和原因。
- 暂停时长只允许 24、168、720 小时。
- 内容已 removed 时返回 409。
- 不允许对管理员执行账号治理。
- 操作、举报状态和审计不能静默部分成功；部分失败必须显式返回。

#### `delete-content`

- 只允许内容作者操作。
- 暂停未到期或封禁账号不能执行。
- 先隐藏内容，再删除媒体，最后删除数据库记录。
- 动态删除必须包含其评论图片。

#### `delete-account`

- 请求体确认词必须为 `DELETE`。
- 管理员不能自助删除。
- 先清理 Storage，再删除 Auth 用户。
- 返回必须明确本机数据仍保留。

## 9. 安全、隐私与合规需求

### 9.1 数据分类

| 类别 | 示例 | 存放位置 | 可见范围 |
|---|---|---|---|
| 本机个人数据 | 清单、检查、表具、读数、宠物 | IndexedDB | 当前设备用户 |
| Auth 身份数据 | 邮箱、密码哈希、会话 | Supabase Auth | 本人；密钥受控的服务端 |
| 公开社区资料 | 昵称、用户名、头像、简介、关注关系 | Supabase | 社区读取范围 |
| 社区内容 | 动态、评论、话题、图片 | Supabase/Storage | 可见内容读取策略 |
| 举报与审计 | 举报原因、处理理由、管理员动作 | Supabase | 举报人本人相应记录；管理员 |
| 管理数据 | 完整邮箱、管理员成员关系 | Auth/admin_accounts | 仅受保护服务端函数 |
| 运维凭据 | service role、SMTP 密码、Cloudflare token | 托管 Secrets/本地受控环境 | 项目所有者与部署系统 |

### 9.2 最小暴露原则

- 公开 API 不返回邮箱。
- 普通 UI 只展示本人掩码邮箱。
- 完整邮箱只在管理员后台按需返回。
- UID 只用于后台查找和管理；普通 App 资料查询不请求 UID。
- 管理员表、Auth 用户表和 service-role 数据不得直接暴露给普通客户端。
- 私密图片通过短时签名 URL 提供，不设置公开 bucket。
- 日志和错误响应不得包含密码、token、SMTP 密码或 service-role key。

### 9.3 鉴权与授权

- 每个受保护操作必须同时验证身份、账号状态和资源授权。
- 管理权限必须由 `admin_accounts` 和 active profile 共同决定。
- 用户 metadata 不能作为后台权限依据。
- 删除用户前必须考虑已有 access token 的有效性；敏感动作继续在服务端查询实时状态。
- 管理员本人改密使用邮箱验证码；管理员重置他人密码使用 Auth Admin API 和审计。
- 普通 App 的 `/#/admin` 不能形成后台访问后门。

### 9.4 CORS 与网络边界

- `admin-manage` 必须限制允许的后台和本地来源。
- 其他 Edge Function 即使允许跨域，也必须依赖平台 JWT 校验和函数内业务授权。
- 生产环境应使用 HTTPS。
- Publishable key 可以公开，但不能替代登录 token。
- Cloudflare 自定义域名应与 Supabase Auth Redirect URL 精确匹配。

### 9.5 审计与问责

- 每次内容治理、账号治理和管理员权限变更都必须写审计。
- 审计必须包含操作者、动作、目标类型、目标 ID、原因和时间。
- 媒体删除数量、暂停时长、上一条状态等必要结果写入 metadata。
- 审计失败不得被当作成功静默处理；接口必须返回部分失败。
- 审计记录只允许管理员读取。

### 9.6 隐私与法律材料

- 上线前必须完成隐私政策、用户协议和社区规范的法律审核。
- 必须补充真实运营主体、联系方式、投诉渠道、处理时限和适用法律。
- 必须披露 Supabase、Resend、Cloudflare 等实际第三方服务及数据区域。
- 不得公开承诺“绝对安全”或“永久免费”。
- 数据删除、更正、访问和投诉请求必须有可执行的联系渠道。

## 11. 部署与运维需求

### 11.1 环境

| 环境 | 用途 | 域名/后端 |
|---|---|---|
| 本地开发 | 功能开发与浏览器验收 | `http://localhost:5173`，本地 `/admin` 仅开发模式 |
| 生产 App | 普通用户访问 | `https://daily.yeecc.cn/` |
| 生产后台 | 管理员访问 | `https://admin.yeecc.cn/` |
| 托管后端 | Auth、数据库、Storage、Functions | Supabase 项目 |

### 11.2 配置变量

| 变量 | 位置 | 要求 |
|---|---|---|
| `VITE_SUPABASE_URL` | 构建环境 | Supabase Project URL |
| `VITE_SUPABASE_ANON_KEY` | 构建环境 | 公开 anon 或 publishable key |
| `RESEND_SMTP_PASSWORD` | Supabase Auth 托管 Secret | 不得进入前端或 Git |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase Edge Function 环境 | 只允许服务端使用 |
| Cloudflare 凭据 | 本地 Wrangler 或 Workers Builds | 使用最小权限 token |

### 11.3 发布顺序

每次涉及社区或后台的发布必须遵循：

1. 备份/确认生产数据状态。
2. 检查迁移历史和待应用变更。
3. 应用向后兼容的数据库迁移。
4. 部署受影响的 Edge Functions 并确认 ACTIVE。
5. 检查 Auth URL、SMTP、OTP、密码和 CORS 配置。
6. 构建前端。
7. 部署 Cloudflare Worker 静态资源。
8. 验证普通 App、后台、登录、RLS 和关键写操作。
9. 记录部署时间、版本和结果。

不得先发布依赖新表或新函数的前端，再延迟配置后端。

### 11.4 Cloudflare 发布

- `wrangler.toml` 必须配置 `daily.yeecc.cn` 和 `admin.yeecc.cn` 两个 Custom Domain。
- `dist/` 必须作为 Workers Static Assets 提供。
- `not_found_handling` 必须为 `single-page-application`。
- 手工发布命令：`npm run build` 后执行 `npx wrangler@4 deploy`。
- 若配置 Workers Builds，生产分支为 `main`，构建命令为 `npm run build`，部署命令为 `npx wrangler deploy`。
- 当前仓库不得假设 push 自动部署，除非控制台已确认 Workers Builds 连接。

### 11.5 Supabase 发布

- 使用 `supabase migration list --remote` 验证本地与远端一致。
- 使用 `supabase db lint --remote` 检查 schema 错误。
- 使用 `supabase db advisors --remote` 检查 RLS、函数和 Auth 安全建议。
- 使用 `supabase config diff` 在推送前审查 Auth/数据库差异。
- Edge Function 使用 `--use-api` 部署，避免依赖本地 Docker。
- 首位管理员必须由项目所有者通过可信管理流程初始化。

### 11.6 回滚

- 前端可回滚到上一 Cloudflare Worker 版本或重新部署上一 Git 提交。
- 数据库迁移应尽量采用向前兼容策略，不依赖破坏性 down migration。
- Edge Function 回滚必须与数据库 schema 兼容。
- 发现权限或数据损坏时优先停止写入、保留审计和备份，再恢复服务。
- 已删除媒体和已移除内容不应被误认为可通过普通回滚自动恢复。

### 11.7 日常运维

- 定期检查 Supabase 用量、Auth 邮件、Storage 容量和 Edge Function 日志。
- 定期验证备份恢复流程和管理员登录。
- 及时审查依赖安全告警；生产依赖优先修复。
- 定期复核管理员名单和未使用管理员。
- 社区开放前复核举报处理时限、联系渠道和内容规范。

## 13. 当前限制与风险

| 风险 | 影响 | 当前控制 | 后续建议 |
|---|---|---|---|
| 没有完整自动化测试套件 | 回归依赖人工 | 构建、lint 和浏览器验收 | 增加 Vitest/Playwright 核心流程 |
| 主 JS chunk 超过 500 KB 原始体积 | 移动网络首次加载成本增加 | gzip 后约 168 KB；后台懒加载 | 继续拆分第三方依赖和社区模块 |
| Workers Builds 未确认连接 | push 不一定更新线上前端 | 产品文档保留手工部署步骤 | 确认构建配置或固定 CI/CD |
| 泄露密码保护依赖 Pro | 免费套餐可能无法启用 | 前端和服务端密码复杂度规则 | 升级套餐并在 Auth 控制台确认 |
| 免费托管存在额度和暂停 | 邮件、存储、数据库或 Worker 可能中断 | 文档披露服务商边界 | 设置额度告警和运营监控 |
| 完整邮箱与管理员操作集中在 Edge Function | 函数 bug 影响治理 | JWT、管理员表、RLS、审计 | 增加函数单元测试和安全回归 |
| PWA 数据只在当前设备 | 清缓存或设备损坏可能丢失 | JSON 备份和导入预览 | 增加定期备份提醒或可选云同步 |
| 社区图片依赖签名 URL 与 Storage 清理 | 删除或权限错误可能导致残留 | 私有 bucket、隐藏优先、partial 结果 | 增加媒体巡检和重试任务 |
| 法律文本仍为草稿 | 不具备直接公开运营条件 | 文档明确上线前补充 | 法律审核并发布正式版本 |
| 无前端错误遥测 | 线上问题发现依赖反馈 | 控制台、后台审计、函数日志 | 引入隐私合规的错误监控 |
| 原设计中的宠物头像/重复提醒未实现 | 与早期愿景存在差距 | 当前需求明确为一次性提醒、无宠物头像 | 纳入后续版本需求 |
| 访客后端可读取公开内容但 UI 要求登录 | 产品呈现与底层能力不完全一致 | 普通 App 始终显示登录引导 | 若未来开放访客浏览需单独验收 |
